# 0.9.0 Release Readiness — Verified Findings and Remediation Plan

Status: proposed
Date: 2026-07-28
Scope: verification of the PR #729 release-readiness review (base `5e6a6f7`,
head `a3dfc88` = current `main`) and the remediation plan for an official
0.9.0 release.

## 1. Verdict

The review substantially holds up. Every finding was re-verified against the
code at `a3dfc88`: 32 of 34 confirmed (several slightly *worse* than
described), one is intentional behavior worth keeping (P2-1), and one is
refuted as a data-loss risk (P1-8 — the strict config schema already fails
that scenario closed; only the error message needs work). The release should
not ship until the items marked **[gate]** in §4 are fixed.

Two claims rest on the reviewer's live databases (row counts in P1-1/P1-2) and
cannot be re-measured here; the code paths that make those rows unreadable are
confirmed, which is what matters for the fix.

The pattern behind most P1s is not 24 unrelated bugs. It is three habits,
applied consistently:

1. **Best-effort where correctness is required.** Archive writes, backups,
   journal persistence, and error classification all degrade to "warn and
   continue" — so a failed safety step silently converts into data loss
   (P1-3, P1-6, P1-7, P2-4).
2. **Mutate first, validate after.** Config/lock writes land before the
   confirmation that can abort; files are rewritten before the Git checks that
   would have refused; secrets are written before the ignored-path assertion
   (P1-10, P1-14, P1-15, P1-16, P1-5).
3. **Identity derived independently at each site.** Bundle/ref identity is
   computed by at least five different fallback chains, and any two of them can
   disagree for the same asset (P1-11, P1-12, P1-13, P1-17, P1-21, P2-3,
   P2-6).

The remediation is therefore mostly *subtraction and reordering*: delete the
warn-and-continue branches, hoist checks above mutations, and collapse the
identity derivations onto the chains that already exist and are correct.

consequence; **CONFIRMED\*** = mechanism confirmed first-hand, one detail

## 3. Principles the fixes must follow

These restate the release owner's constraints; every item in §4 was chosen
against them.

- **Prefer subtraction.** Most fixes below delete a branch, delete a check
  from the wrong place, or reorder existing lines. New code is limited to the
  migrate tool's row-normalization pass, which is where legacy knowledge is
  *supposed* to accumulate.
- **akm-migrate is the one-shot upgrade tool.** All legacy-format knowledge
  (v1 task-history metadata, pre-target proposal rows, old config/lock shapes,
  legacy ref grammar) lives in `scripts/akm-migrate` only. The main CLI stays
  strict and current-format-only — no tolerant readers, no fallback decoders.
- **The migrate tool must be boring:** idempotent, re-runnable after any
  crash, incapable of losing data. Concretely: persist intent before every
  destructive step; never reinterpret an I/O failure as "data to skip"; never
  report `current` while unmigrated data remains.
- **No gold-plating.** No new frameworks, no speculative config, no
  generalized "transaction manager". Where a design decision is defensible
  as-is (P2-1), keep it and say so.

## 4. Remediation plan

Ordered by workstream; **[gate]** marks items that block tagging 0.9.0.
Effort: S = < ~1 h, M = half-day, L = day+.

### WS-1 — akm-migrate: complete, repeatable, no data loss

The theme: apply must leave *zero* data the 0.9.0 CLI refuses to read, must
fail loudly on anything it could not migrate, and must be safely re-runnable
after a crash at any line.

1. **[gate]** (P1-1, P1-2, M) **Add a state-row normalization step to
   `apply`.** One idempotent pass over state.db:
   - `proposals`: for rows whose `metadata_json` lacks `proposedTarget` /
     `changes`, or whose `ref` is not canonical — derive `proposedTarget` from
     `stash_dir` + the same bundle-root map the FS import already builds,
     synthesize `changes` exactly as `proposal-fs-import.ts:319-322` does, and
     canonicalize refs with the tool's existing legacy-ref machinery. Rows that
     cannot be mapped are counted and reported as an apply error (see item 3),
     never silently skipped.
   - `task_history`: wrap rows whose `metadata_json` is not
     `metadataVersion: 2` into the v2 envelope. Resurrect the deleted v1
     decoder from git history *into the migrate tool* — this is precisely the
     legacy knowledge that belongs there, not in the CLI.
   - **Fix the tool's own writer**: the JSONL import
     (`migrate-storage.ts:523-539`) must emit `metadataVersion: 2` and fold
     the legacy `profile` field into the v2 shape instead of emitting an
     unknown key the decoder rejects.
   The CLI's strict readers stay exactly as they are.
2. **[gate]** (P1-1, S) **Make `migrate status` check row formats, not file
   presence.** Replace the `present ⇒ "current"` state.db check
   (`config-migrate.ts:1207`) with the same cheap `SELECT COUNT(*)` predicates
   the normalization step uses. Status must not say `current` while rows the
   CLI cannot read remain.
3. **[gate]** (P1-7, S) **Stop classifying I/O failures as malformed data.**
   In `readLegacyProposalFile`, the sidecar fold, and the reserved-rename walk:
   only `ENOENT` and parse failures qualify as skip-with-warning; every other
   error (EACCES, EIO, …) aborts apply with the error, leaving the journal in
   place so a re-run retries. One small shared predicate, three call sites.
4. **[gate]** (P1-6, S) **Persist rename pairs before renaming.** In the
   reserved-rename step: collect all `(from, to)` candidates, append them to
   the persisted content-migration report, *then* execute the `renameSync`
   loop. On resume, a persisted pair whose `from` is gone and `to` exists is a
   completed no-op (`collisionSafeTarget` is deterministic). This closes the
   rename→persist crash window; the existing persist→re-key ordering already
   covers the rest.
5. (P1-8, S) **Give mixed config shapes an actionable error.** Verification
   showed the schema already fails this closed (no data loss — see §2), so no
   behavioral fix is needed. What remains is the circular message: detect
   `bundles` + old-key coexistence early in apply/status and say "remove the
   retired keys X, Y (or restore the pre-apply backup)" instead of "run
   `akm-migrate apply`". Optionally delete the redundant
   `if ("bundles" in raw) return []` in `migratedLockEntries` (line 256's
   `hasOldSourceShape` check already covers it); the twin guard in
   `migrateConfigSourcesToBundles:292` is the idempotence check and stays.
6. **[gate]** (P1-23, S) **Spawn `process.execPath`, never the literal
   `"bun"`.** The migrator is already driver-portable; delete the conditional
   in `migration-tool.ts:37`. Add the Node-only-PATH invocation to the release
   smoke (§6).
7. (P1-22 provenance, S) **Migrated active workflow runs**: covered by WS-5
   item 2 (the CLI-side fix is strictly simpler than teaching the migrator to
   synthesize plans; abandoning a pre-plan run is the *correct* semantic).

### WS-2 — consolidate: never destroy the last copy

1. **[gate]** (P1-3, S) **Archive failure aborts the op.** In `archiveMemory`
   callers (merge 1984-2005, delete 2222-2243): if `archiveMemory` returns
   `undefined`, skip the delete, record a skip reason, and leave the journal
   entry incomplete. Delete the warn-and-continue path. The invariant is one
   sentence: *no live memory is deleted unless its archive copy was written.*
   (With that invariant, `backupFile`'s best-effort status is acceptable as a
   second layer; it no longer stands between the data and oblivion.)
2. **[gate]** (P1-4, S) **Consume exactly what was merged.** Two small,
   same-direction changes: constrain `CONSOLIDATE_PLAN_JSON_SCHEMA`'s
   `secondaries` to `maxItems: 1` so the planner can no longer propose
   multi-secondary merges, and make the executor archive+delete only
   `secondaries[0]` — the one memory `generateMergedContent` actually read —
   skipping the rest with an explicit reason (defends journaled/in-flight
   plans that predate the schema change). This aligns everything with the
   function's documented single-secondary design instead of building multi-way
   merging (gold-plating). Rewrite the golden at
   `goldens-consolidate-ops.test.ts:325-346` to assert secondary B *survives*.
   If multi-secondary plans should eventually merge fully, that is a 0.9.x
   feature; 0.9.0 only has to stop deleting unread content.
3. **[gate]** (P1-20, S) **Advance the watermark only on real progress.** The
   success signal already exists on the result: gate the emit on
   `consolidation.processed - consolidation.failedChunkMemories > 0` instead
   of `processed > 0` (`preparation.ts:400`), add the target source to the
   event metadata, and filter on it in the pool-delta read
   (`preparation.ts:193-197`). No new fields.
4. (P1-19, S) **Thread `opts.signal` and the resolved timeout into both
   `callStructured` sites** (and the distill equivalent). The plumbing already
   delivers the signal to the function; it just stops one call short.
5. (P1-18, M) **Apply the budget cap before embedding.** Hoist the cold-start
   estimate above `clusterMemoriesBySimilarity` and cap the *memory pool*
   (chunk count is `ceil(pool/chunkSize)`, so the same arithmetic works); the
   estimate should include embedding cost for cache-miss pools. No new
   mechanism — the same check, moved up.
6. **[gate]** (P1-5, S) **Gate every improve write behind the plan.** Drop
   `fix: true` from the Phase 0.5 lint call (`preparation.ts:815`) — improve
   reports lint findings; it does not silently rewrite and delete assets
   outside any configured process. (If auto-fix-during-improve is wanted
   later, it becomes an explicit, gated process — not a side effect.) Then
   audit the pipeline (`preparation.ts`, `distill.ts:688-706`) for any other
   write reachable with all processes disabled. A fully-disabled improve run
   must be read-only.

## 5. Explicit non-goals (anti-gold-plating)

- **No tolerant/legacy readers in the CLI.** Migration completeness (WS-1) is
  the fix; the strict readers are a feature. If a strict reader still trips
  post-migration, that is a migrate-tool bug to fix there.
- **No multi-secondary merge engine.** WS-2.2 stops the data loss; richer
  merging is optional future work.
- **No new transaction framework.** The existing txn/journal mechanisms are
  sufficient once the warn-and-continue branches are removed.
- **P2-1 stands as designed** (preserve rows for an unavailable root, warn).
  If desired later, `show`'s ENOENT for an indexed row can hint "root
  unavailable or stale index" — cosmetic, 0.9.x.
- **No `akm migrate` UX redesign.** The embedded `akm migrate` passthrough
  stays; it just spawns the current runtime (WS-1.6). The standalone
  invocation remains the documented upgrade path.

2. Re-run the review's own verification suite as the tag gate:
   `bun run build`, `bun run check` (unit must be 0-fail — P1-24 fixes the two
   known), `bun run test:integration`, package acceptance + global-install
