### Added

- **`akm task list` is a delegating alias for `akm search --type task`, and
  `akm info` exposes `dataDir`/`configDir`/`cacheDir`/`stateDir` (#951).**
  0.9.0 removed `task list` because it was a second, redundant
  implementation of task listing, not because the spelling itself was
  off-limits; every operator and script in a recent fleet review still
  reached for `list` first. It now delegates to the exact same
  `akmSearch`/`parseSearchSource` path `akm search --type task` uses, with
  the query, `--limit`, and `--from` flags passed through and the same
  envelope/`results` alias — no second implementation to keep in sync.
  `task show`/`task remove` stay retired. Separately, `akm info` now
  reports akm's resolved data/config/cache/state directories alongside
  `bundleDir`, so a script can read `akm info --format json | jq -r
  .dataDir` instead of hardcoding a path that differs between a host
  install and a container.

### Fixed

- **`akm show env/<name>` prints key names in plain-text output, and the
  cron scheduler backend truncates its raw log instead of appending
  forever (#951).** The plain-text `show` renderer never read the response's
  `keys` field, so the default (non-`--format json`) output for an env asset
  showed generic boilerplate with no way to audit which keys a script
  depends on; `--format json` was already correct. Separately, the crontab
  entry cron.ts installs for each task redirected its raw stdout/stderr with
  `>>` (append) forever, so `tasks/logs/<id>.log` grew without bound — a
  two-month-old crash line was still surfacing in `grep error` across every
  container. That file is a bootstrap safety net only, meant to catch akm
  crashing before it reaches its own per-run log (which already separates
  runs and keeps history in `logs.db`); the redirect now truncates (`>`)
  instead, so the file always holds exactly the latest run's raw output. An
  already-installed row (from before this change, or written by an older
  akm binary mid-upgrade) still parses correctly. `launchd`'s equivalent log
  path is OS-managed append-only with no truncate mode, so it is left
  unchanged — matching it would require wrapping the invocation in a shell
  script, a materially bigger change not justified by the Linux-only fleet
  evidence behind this issue; `schtasks` does not redirect at all and is
  unaffected. Also removed the false `akm curate --rerank` / "curate
  reranks by intent" claims from the docs and the `curate` command's own
  description — `akm curate` never implemented reranking (`curate_rerank`
  was removed in 0.8.0), closing out Q-10 in the 0.9.0 docs/code-drift
  register.

A `rerank` engine kind (a config schema arm plus an HTTP client and
curate/search wiring for the lab's cross-encoder reranker from the same
fleet review) is real feature work, not a consistency nit, and is deferred
to its own issue. Health-report Discord embed field/value clamping is out
of scope for this repository: the referenced script does not ship here.
