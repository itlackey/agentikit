### Added

- **`akm workflow list`/`status --all-scopes` (#942).** Workflow runs are partitioned by `scope_key`, a hash of the working directory a run was started from — so a scheduled task (cwd `$HOME`) and a human shell (cwd inside the stash) can each believe a ref has no active run and each start one, while `akm workflow list` from either scope shows only its own. `--all-scopes` searches every scope instead of only the current one, and `list`'s (and the ref-fallthrough path of `status`'s) JSON envelope now always carries a top-level `scopeKey` naming the scope that was searched (`null` under `--all-scopes`) — so an empty `runs: []` is no longer indistinguishable from "nothing anywhere". Both are additive; default output is unchanged.

### Fixed

- **Starting a workflow ref that already has an active run in a different scope now warns instead of silently duplicating it (#942).** `akm workflow run <ref>`'s per-scope concurrency guard is unchanged by design — two unrelated projects sharing one `state.db` can each run the same-named workflow independently — but before starting a new run it now also checks for an active run of the same ref in any OTHER scope and, if one exists, adds a warning naming that run's id, scope, and start time, with the same `akm workflow run <id>` / `akm workflow abandon <id>` remedy the same-scope guard already gives. The three existing "already active" guard messages (the two `resolveRunSpecifier` refusals and `publishWorkflowRunV4`'s `RESOURCE_ALREADY_EXISTS`) now also name the blocking run's scope, not just its id. `akm workflow status`/`resume`/`abandon <run-id>` already worked from any scope (#919) and are unchanged.
