### Added

- **`akm improve report` and a per-run `usageReport` field answer "which engine did each process use, how much did it cost, and which processes made zero calls" without hand-written SQLite (#944).** Every `chatCompletion` attempt was already persisted as an `llm_usage` event (#576), but reading it back meant querying `state.db` directly, and "why did a process make zero calls" was only reconstructable from stderr logs or `improve_skipped` events. A new `summarizeLlmUsageCrossTab` aggregator groups a window's `llm_usage` events into a process x engine x model cross-tab (`calls`, a new `failures` count, token totals, wall time); `finalizeImproveResult` folds it together with the resolved process routing table (#947) into `usageReport: {byProcessEngineModel, noCalls}` on every live run's result, omitted when both would be empty. `noCalls` lists every LLM-backed process the active strategy enabled but that made zero calls, each with a `reason` drawn from the existing skip-reason vocabulary (`"engine_unavailable"`, `"autonomy_gated"`, `"strategy_filtered_all_passes"`, a reflect/distill dominant skip reason, or `"no_signal"`) — never a fabricated category. The same table is printed to stderr after every real run. `akm improve report [--run <id>] [--since <window>]` reads it back: with no flags, the most recent real run; `--run <id>`, one specific run; `--since <window>`, summed across every real run in the window. A run recorded before 0.9.15 has no persisted `usageReport` — the command recomputes the cross-tab from that run's own `llm_usage` events instead of erroring, and adds a `notes` entry saying eligibility reasons could not be recovered rather than fabricating them. `"report"` is a reserved `improve` scope value, matching zero real assets, so it dispatches to the report before any lock, log, or index side effect — the same precedent the retired `canary` scope set.
